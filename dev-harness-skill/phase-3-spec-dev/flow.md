# Phase 3：Spec & 开发

> **定位：** 基于 PRD + 架构设计，对单个任务做 Spec 分析并完成开发。
> **Agent 帽子：** 需求分析师 → 技术架构师 → 开发者 → 测试工程师
> **前置：** Phase 1 的 PRD + Phase 2（如有）的技术架构和任务拆解
> **输入：** 单个任务（PRD + 项目上下文 + 架构设计）
> **产出：** Spec → 技术设计 → 源代码 → 测试报告

---

## 流程总览

```
PRD + 项目上下文 + (架构设计)
    ↓
阶段 ① Spec 生成（决策树 → 概要 → 确认 → 详细 Spec）
    ↓
阶段 ② 技术设计（API + DLL + DB，一份文档）
    ↓
阶段 ③ 前端设计（条件性：仅复杂逻辑时触发）
    ↓
阶段 ④~⑧ 垂直切片 TDD 循环
    ├── ④ 任务拆解（本切片）
    ├── ⑤ 写测试代码
    ├── ⑥ 跑测试（RED）
    ├── ⑦ 编码实现
    └── ⑧ 编译 + 测试通过（GREEN）
    ↓
阶段 ⑨ 集成验证（可选）
    ↓
PR review + 验收
```

---

## Spec 决策树（阶段 ①）

参见 `rules/decision-boundary.md`。

核心原则：
- **能推导的 → Agent 定**（项目上下文有约定、行业标准做法、改动成本 ≤50 行代码）
- **影响大的 → 带选项问**（数据策略、范围决策、架构选型、外部集成）
- **每次 ≤ 3 个决策点**
- **先概要后详细**：STEP 3 概要确认 → STEP 5 展开详细 Spec

---

## TDD 铁律

1. 必须先跑出 RED 再写实现
2. RED 失败原因是「代码未实现」而非测试写错 → 否则先修测试
3. GREEN 不通过时改代码，不改测试
4. 每切片完成后通报用户进度

---

## 设计冲突处理

1. 先看技术设计文档——它是约定
2. 设计有问题 → 更新设计文档再编码
3. 实现细节选择 → Agent 自主决定
4. 影响设计的冲突 → 升级给用户 `[偏离 · 类型]`
