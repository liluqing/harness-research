# Harness 本质：Agent 像公司一样运作

> ⚠️ **阅读任何 Harness 相关材料前，先读这篇。**
> 这是所有讨论的起点，后续所有分析不能偏离这个本质。

---

## 一、核心洞察（2026-06-07 对话中确立）

**错误的旧理解：** Harness 是放在项目里的配套文件（AGENTS.md + scripts/ + docs/ 目录结构 + 评估体系）。

**正确的本质：** Harness 是一套让 Agent **像一家正规公司一样运作**的"组织系统"，覆盖从目标设定到最终交付的全链路。

---

## 二、比喻：Agent 是一家公司

### 普通 Agent = 个体户

```
prompt → Agent → 输出（看心情，不稳定，质量随缘）
```

一个人，没有流程，没有分工，没有质量标准，今天干得好明天干得差。

### 有 Harness 的 Agent = 一家正规公司

```
需求 → [ 公司运作系统 ] → 稳定可预期的产出
                     ↑
                10 大要素保障
```

## 三、10 大要素

| # | 要素 | 公司里对应什么 | 没有会怎样 |
|:-:|------|--------------|-----------|
| **①** | **目标与方向** | OKR、项目立项、需求文档 | 不知道做什么，瞎忙 |
| **②** | **角色与分工** | 组织架构、岗位职责 | 谁该干什么分不清 |
| **③** | **流程与方法** | SOP、审批流、协作流程 | 产出参差不齐 |
| **④** | **规范与标准** | 编码规范、设计规范、合规 | 质量不可控 |
| **⑤** | **信息与知识** | Wiki、知识库、复盘文档 | 踩过的坑下次继续踩 |
| **⑥** | **质量与验证** | QA、Code Review、CI/CD | Bug 流入生产 |
| **⑦** | **工具与基础设施** | JIRA、GitHub、Jenkins | 纯手工作业，效率低 |
| **⑧** | **决策与升级** | 汇报线、决策权限 | 卡住没人拍板 |
| **⑨** | **沟通与协作** | 周会、日报、文档交接 | 前后端各搞一套 |
| **⑩** | **追溯与改进** | 复盘、事后分析 | 同样问题反复出现 |

## 四、之前研究的偏差

之前研究 fanlw0816/Arthurescc/ffy6511 的仓库后，我理解的 Harness 只覆盖了：

```
✅ ③ 流程与方法    → 文档流水线
✅ ④ 规范与标准    → AGENTS.md 编码规约
✅ ⑥ 质量与验证    → Generator-Evaluator 分离 + Sprint Contract
✅ ⑦ 工具与基础设施 → scripts/、hooks/、Makefile
```

**但用户真正关心的核心是：**

```
🔥 ① 目标与方向    → 需求怎么变成可执行的 contract？
🔥 ⑤ 信息与知识    → 知识在 Agent 和人之间怎么传递和沉淀？
🔥 ⑧ 决策与升级    → 什么 Agent 自己定，什么升级给人？
🔥 ⑨ 沟通与协作    → 多阶段、多 Agent 之间怎么接力？
```

**以及它们如何衔接：**

```
需求(人) ──①──▶ 产品文档(Agent+人) ──①──▶ 技术文档(Agent) ──①──▶ 实现(Agent) ──①──▶ 交付(Agent+人)
                │                       │                       │                    │
               ⑤ 知识沉淀              ⑧ 人决策                ⑨ 协作              ⑩ 追溯
```

## 五、重要修正：角色不是必须的（2026-06-07 补充）

**关键修正：** 小公司可以没有产品经理，开发兼测试，一个人干三个人的活。类比到 Agent——

### 不要多 Agent，要把分工做成流程

**之前的错误倾向：** 一提到"角色与分工"就想到 Planner Agent、Generator Agent、Evaluator Agent 各自独立 —— 这是大公司的架构，对于小项目太重了。

**正确的思路：**

```
不是这样的多 Agent 架构：
         ┌──────────┐
         │ Planner  │  (独立的 Agent)
         ├──────────┤
         │ Generator│  (独立的 Agent)
         ├──────────┤
         │ Evaluator│  (独立的 Agent)
         └──────────┘

而是同一个 Agent 在不同阶段切换"帽子"：
           
Agent (同一个人)
  │
  ├─ [需求模式]   → 焦点：理解业务、追问模糊点、结构化需求
  ├─ [产品模式]   → 焦点：生成 PRD、细化功能规格
  ├─ [技术模式]   → 焦点：推演架构、设计 API/DB
  ├─ [开发模式]   → 焦点：写代码、跑测试、自验证
  └─ [交付模式]   → 焦点：用户手册、发布说明
```

### 核心设计原则

**把分工做成流程，用 scale 让 Agent 聚焦当前阶段。**

- 不是让不同 Agent 干不同的事
- 而是让同一个 Agent 在**不同阶段戴不同的"帽子"**
- 每顶"帽子"告诉 Agent：你现在是什么角色，关注什么，产出什么，按什么标准检查

### 对 10 大要素的影响

```
② 角色与分工 → ❌ 不是多 Agent 分工
               ✅ 而是同一 Agent 的阶段切换（戴帽子/脱帽子）

③ 流程与方法 → 定义了"什么时候戴什么帽子"
```

### 设计上的体现

每个阶段应该有一个**焦点文档/焦点提示**，告诉 Agent：

```
你现在处在 [需求阶段]。
你的角色是：产品分析师。
你需要关注的：理解原始需求，追问模糊点，生成结构化需求文档。
你的产出物：docs/requirements/01-用户故事.md
你的检查清单：[ ]
```

Agent 完成这个阶段 → 递交产出 → 等反馈 → 切换到下一个阶段 → 换一顶帽子。

## 六、讨论中需要始终遵守的原则

1. **不从目录结构出发，从公司运作要素出发。**
   - 不问"AGENTS.md 应该写什么"，而是问"Agent 需要什么信息来理解目标和规矩"

2. **不是多 Agent，而是单 Agent 换帽子。**
   - 分工做成流程，用阶段切换来聚焦，不引入多 Agent 复杂度

3. **不是替人做事，是帮人确保链路不断。**
   - Harness 的核心价值在于"需求到产品的文档链没断"，而不是 Agent 多能干

4. **人机分工是设计重点，不是附加项。**
   - 每个阶段都要想：这个决策 Agent 能自己定吗？还是必须升级给人？

5. **不局限于"一个项目"的范畴。**
   - 公司可以同时接多个项目，Agent 也可以。跨项目的知识共享和隔离也需要考虑
