# 文档链路中的人机分工

> 核心问题：在整个"需求→产品"的文档链路中，
> 哪些环节必须人介入，哪些 Agent 能自己跑？

---

## 二、逐层分析

### 第 1 层：需求阶段

```
输入：人的想法 / 口头需求 / 简单描述
输出：结构化需求文档 + 用户故事 + 验收标准

┌────────────────────────────────────────────┐
│  👤 人必须做：                               │
│    · 说出"我要什么"（业务目标、核心诉求）      │
│    · 确认"对和不对"（方向是否理解正确）         │
│                                             │
│  🤖 Agent 能做：                             │
│    · 追问模糊点（"具体什么场景？优先级？"）     │
│    · 结构化输出（用户故事格式）                │
│    · 识别需求中的矛盾或遗漏                    │
│    · 生成第一批验收标准（待确认）              │
│                                             │
│  ❌ Agent 不能：                              │
│    · 替人决定做什么                           │
│    · 理解没说出来的潜台词                      │
└────────────────────────────────────────────┘

📍 人机交互点：人给原始需求 → Agent 追问 + 结构化 → 人确认
```

### 第 2 层：产品阶段

```
输入：结构化需求 + 验收标准
输出：PRD、功能规格

┌────────────────────────────────────────────┐
│  👤 人必须做：                               │
│    · 确认功能优先级（P0/P1/P2）              │
│    · 确认用户体验方向（交互方式、设计风格）     │
│    · 拍板有争议的产品决策                      │
│                                             │
│  🤖 Agent 能做：                             │
│    · 从需求生成 PRD 初稿                      │
│    · 细化每个功能的详细行为（正常流程+异常）    │
│    · 补充边界条件和错误场景                    │
│    · 检查 PRD 是否覆盖所有需求                 │
│                                             │
│  ❌ Agent 不能：                              │
│    · 替人做价值判断（这个功能值不值得做）        │
│    · 理解产品的商业策略和长期愿景               │
│                                             │
└────────────────────────────────────────────┘

📍 人机交互点：Agent 生成 PRD draft → 人评审修改 → Agent 细化规格
```

### 第 3 层：技术阶段

```
输入：PRD + 功能规格
输出：架构设计、API 契约、DB 设计、技术决策

┌────────────────────────────────────────────┐
│  👤 人必须做：                               │
│    · 确认关键技术选型（数据库选型、框架选择）   │
│    · 对成本/性能/安全有重大影响的决策           │
│                                             │
│  🤖 Agent 能做：                             │
│    · 从功能规格推导技术方案                    │
│    · 生成完整的 API 契约                      │
│    · 设计数据库表结构                         │
│    · 记录架构决策（ADR）                      │
│    · 自动检查技术方案是否覆盖所有功能点          │
│    · 前后端 API 一致性校验                     │
│                                             │
│  ❌ Agent 不能：                              │
│    · 替人承担技术风险（选错了谁负责）            │
│    · 理解组织特有的基础设施限制                  │
│                                             │
└────────────────────────────────────────────┘

📍 人机交互点：Agent 出技术方案 → 人评审关键决策 → Agent 细化
```

### 第 4 层：实现阶段

```
输入：技术方案 + 设计文档
输出：代码 + 测试 + Sprint Contract 验收结果

┌────────────────────────────────────────────┐
│  👤 人必须做：                               │
│    · PR review（代码审查，>20% 的逻辑改动）    │
│    · 最终验收测试（UAT）                      │
│                                             │
│  🤖 Agent 能做：                             │
│    · 从 contract 出发，拆解任务               │
│    · 编写代码                                │
│    · 编写测试                                │
│    · 自启动验证（跑测试 + lint + 健康检查）     │
│    · 自检是否达成 contract 的验收标准          │
│    · 修复失败的测试                          │
│                                             │
│  ❌ Agent 不能：                              │
│    · 替人做 final sign-off                    │
│                                             │
└────────────────────────────────────────────┘

📍 人机交互点：最少。Agent 完成 → 人 PR review + 验收
```

### 第 5 层：交付阶段

```
输入：代码 + 测试结果
输出：用户手册、发布说明、运维文档

┌────────────────────────────────────────────┐
│  👤 人必须做：                               │
│    · 确认发布范围和兼容性说明                  │
│    · 最终审核文档的语气和准确性                 │
│                                             │
│  🤖 Agent 能做：                             │
│    · 从代码变更自动生成用户手册更新             │
│    · 生成发布说明（基于 git log + changelog）  │
│    · 更新运维文档                             │
│    · 检查文档与代码的一致性                     │
│                                             │
└────────────────────────────────────────────┘

📍 人机交互点：Agent 生成 → 人快速审阅
```

## 三、核心结论：Agent 能跑多少？

### 按阶段统计

| 阶段 | 人介入次数 | Agent 自主度 | 说明 |
|------|:---------:|:-----------:|------|
| 需求 | 2 次（给需求 + 确认） | ⭐⭐ | Agent 辅助结构化和追问 |
| 产品 | 2 次（定优先级 + 审 PRD） | ⭐⭐⭐ | Agent 生成 draft + 细化 |
| 技术 | 1 次（审关键决策） | ⭐⭐⭐⭐ | Agent 可以自主完成多数技术设计 |
| 实现 | 1 次（PR review） | ⭐⭐⭐⭐⭐ | **Agent 自主度最高的阶段** |
| 交付 | 1 次（终审） | ⭐⭐⭐⭐ | Agent 生成，人快速过一遍 |

### 按工作量统计

```
人必须做的事情：  约占总工作量的 15-20%
    · 原始需求定义
    · 关键决策拍板（优先级、技术选型、UX方向）
    · 评审和 sign-off（PRD 评审 + 技术评审 + PR review + UAT）

Agent 能自主做的：约占总工作量的 80-85%
    · 需求结构化和追问
    · 产品文档起草和细化
    · 技术方案推导和文档化
    · 编码和自测
    · 交付文档生成
```

## 四、Harness 在这个分工中的作用

Harness 要解决的不仅是"Agent 能不能跑"，更是 **人在哪里介入、怎么介入、以什么形式介入**。

### Harness 定义的人机接口

```
Agent 完成 → 生成 Review Artifact → 人评审 → 人反馈 → Agent 修改 → 通过

具体形式：
  · PRD 评审：Agent 生成 PRD.md → 人评论 → Agent 修改
  · 技术评审：Agent 生成 ADR → 人在 GH Issue 确认 → Agent 继续
  · PR review：Agent 提交 PR → 人 review → Agent 修 comment
```

### Harness 要保证的

1. **Agent 跑完一段后，产出物是"人可直接评审"的质量**
   - 不是草稿，是"可评审版本"
   - 有明确的 check 清单让人对照

2. **人在介入时，决策成本尽可能低**
   - 不是让人从头读一遍，而是让人关注关键决策点
   - Agent 标注"这里我做了选择，理由是 XXX，需要你确认"

3. **人确认后，Agent 能无缝继续**
   - 评审意见被结构化记录
   - Agent 根据反馈调整后继续下一阶段

---

## 五、一句话总结

> **需求从人来，关键决策人拍，代码 Agent 写，结果人验收。**
>
> Harness 的作用不是让 Agent 取代人，
> 而是让 Agent 把 80% 的"文档推导 + 编码执行"自动化，
> 让人只做那 20% 必须人做的判断和决策。
