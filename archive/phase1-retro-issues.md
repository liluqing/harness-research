## 问题列表

### 🔴 问题一：STEP 3（概要）和 STEP 4（原型）的顺序在实际中倒置

**现象：** 用户说「你把两个方案的原型都做出来我对比」→ 原型跑到了概要前面。对于有 UI 的产品，可视化是比文字概要更高效的沟通语言，用户自然地先看原型再确认概要。

**根因：** flow.md 的流程设计假设了「先文本确认再可视化」，对所有产品形态一刀切。但有 UI 的产品原型天然是更好的对齐工具。

**建议改法：** flow.md STEP 3 加一条规则——Agent 根据 STEP 0 的产品形态判断：
- 有 UI（B 端/C 端/小程序/营销页）→ **先出原型 → 再出概要**
- 纯 API/CLI → 先出概要 → 原型跳过
不硬性规定顺序，让 Agent 根据产品形态自动判断。

---

### 🟡 问题二：PRD 概要模板缺「产品骨架」（流程+状态+实体）

**现象：** 最初的概要只有功能列表和决策点，缺核心流程、状态流转、核心实体。用户指出「概要应该包含这些」——这三个东西是开发前必须对齐的，否则 Phase 3 的 Agent 不知道状态机怎么设计。

**根因：** 设计 Phase 1 时注意力偏向「流程机制」（决策树/退出标准/交接清单），忽略了概要本身的**内容标准**——什么信息密度才算一份合格的概要。

**建议改法：** 已临时创建 `prd-summary.md` 模板（含产品三问、核心流程、状态流转、核心实体、功能范围、业务规则、决策汇总）。全链路结束后正式集成到 flow.md，并更新验收标准。

---

### 🟡 问题三：STEP 2 决策树缺「定位校准」步骤

**现象：** Agent 问了 3 个决策点后，用户的第一个回答完全改变了产品定位——「服务于 Harness 开发流程，有两类用户：我和 Agent」。这说明 Agent 最初的需求理解有方向性偏差，但决策树没有在提问前做校准检查。

**根因：** 决策树设计假设 Agent 对需求的理解大致正确、只需要澄清细节。但实际中 Agent 可能理解偏了方向，需要先校准大方向再问细节。

**建议改法：** STEP 2 开头加一步「定位校准」：
> Agent 生成需求快照后，在进入决策树提问前，先用一句话复述对产品的理解（形态+用户+核心场景），发给用户：
> 「我理解你要做的是一个 **<产品形态>**，主要给 **<用户>** 用，核心场景是 **<场景>**。方向对吗？」
> 用户确认方向 → 再进入决策树提问。如果方向偏了，先校准再提问。
