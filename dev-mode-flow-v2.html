🔍 阶段 ① 内部流程：决策树 → 概要 → 确认 → 详细 Spec

🧠 Spec 生成决策树（Agent 内部执行，只输出结果给人）

STEP 1
读取 PRD + 项目上下文
读 PRD、已有代码、设计文档、项目约定。提取所有待决策点。
▼
STEP 2
逐项走决策树：这个决策点谁来定？
⬏
⬐
⬎
🟢 分支 A：Agent 自主决策
项目上下文可推导
已有代码结构、既有约定、行业通用做法能明确推导的决策。
Agent 直接定，一句话告知用户方案（不提问）。
例：表名用 user 还是 users？→ 项目已有表都用单数，跟单数。
🟠 分支 B：必须问用户
影响大 / 需求模糊
对架构、范围、体验有重大影响；或 PRD 完全没提、Agent 无法推断。
给出 2~3 个选项 + 建议，让用户选。
例：删除用户后历史数据保留还是级联删除？
→ A. 软删除，保留数据 B. 硬删除+归档 C. 仅解关联
→ 建议 A，原因：数据可追溯，风险最低
▼
STEP 3
汇总输出：Spec 概要（几句自然语言）
把决策结果整合成一段话，覆盖：做什么、核心流程、关键决策、边界说明。
含：Agent 自己定的决策（一句话告知）+ 需要用户选的决策（带选项）。
不要写详细 Spec——概要通过后再展开。
📤 输出格式 → 飞书消息发给用户确认
▼
STEP 4 · 👤 人介入
用户确认概要
用户确认方向、回答决策问题。Agent 根据反馈调整后→ 进入详细 Spec 撰写。
▼
STEP 5 · 🤖 Agent 自主
展开详细 Spec
基于确认的概要，写完整的用户故事、正常流程、异常边界、验收标准。
写入 specs/xxx-spec.md，附在 PRD 旁。
📄 产出 → specs/功能名-spec.md
✅
能推导的 → 直接定，顺带告知
「技术设计阶段表名会用 xxx，跟项目已有表命名一致。」
不提问，一句话带过。用户如有异议自然会纠正。
🎯
要问的 → 给选项 + 建议
不要说「要不要做 XX」，要说「XX 有 A/B/C 三种方式，建议 A，因为...。你怎么看？」
每次不超过 3 个决策点，太多说明 PRD 本身需要回炉。
📏
问之前先过脑子
不是所有模糊点都要问。问自己：这个决策对最终产出的影响超过 10% 吗？不超过 → Agent 自己定。
判断标准：影响范围 × 不可逆程度。
🎯 人工决策点 & 决策内容
决策点 ① Spec 概要确认 用户决策
📋 方向判断 Spec 概要里的功能范围对不对？有没有漏掉核心场景？
🔀 关键决策选择 Agent 提出的 2~3 个二选一/三选一决策（范围/策略/取舍）
⚠️ 边界取舍 异常场景的处理粒度够不够？并发、幂等要不要这版做？
💡 Agent 自主决策确认 Agent 基于上下文自己定的决策是否认可？（有异议可纠正）
决策点 ② 技术设计确认 用户扫一眼（推荐）
🏗️ 架构方向 API 结构、实体关系是否与已有系统一致？
🔑 关键规则 业务规则（级联删除、唯一约束）理解对吗？
🗄️ 数据模型 表结构、索引设计是否合理？有没有遗漏字段？
决策点 ③ PR Review + 验收 用户决策
✅ 功能验收 代码实现的逻辑是否满足 Spec 的验收标准？
🔍 代码质量 命名、结构、错误处理、日志是否达团队标准？
🧪 测试覆盖 测试是否覆盖了关键路径和边界？Mock 策略是否合理？
🚀 合并决策 是否合并？是否需要补充集成测试？
决策点 ⚡ 按需升级（Agent 请求） 发生频率：低
🤷 设计冲突 编码中发现设计文档有歧义/矛盾，Agent 无法自行判断
🔀 多方案选择 技术实现有 2+ 个合理路径，各有 trade-off
🚨 风险升级 发现安全/性能/数据一致性等可能需要人介入的问题
🤖 Agent 自主完成区

🟢 以下环节 Agent 全程自主，无需等待人工确认

📐技术设计撰写
基于已确认的 Spec，自动推导 API 契约、领域模型、DB 设计。遵循项目既有架构约定。
→ docs/design/xxx-design.md
🎨前端设计（条件性）
仅当满足触发条件（多步状态流转/≥3交互分支/实时协作）时自动产出组件树和交互流程。
→ docs/ui/xxx-ui.md（条件触发）
📋切片任务拆解
将功能按 API 端点拆为独立切片，每切片产出任务卡片。Agent 自主决定切片顺序（依赖优先）。
→ 会话内任务卡片
✍️写测试代码（TDD-RED）
为当前切片编写可执行测试代码。覆盖正常流程+边界+异常。跑一遍确认全部失败（RED）。
→ src/test/.../*Test.java
💻编码实现（TDD-GREEN）
按任务卡片逐项编码，目标是最小实现让测试变绿。遇到设计冲突时升级给人。
→ src/main/.../*.java
🔨编译 + 测试运行
编译验证 0 error，运行测试确认全绿。失败则回到编码阶段修复（不改测试）。
→ 编译报告 + 测试报告
📢进度通报
每完成一个切片，自动向用户通报进度。「切片 X 完成 ✅，开始切片 Y ⏳」
→ 飞书消息通知
🔄文档同步更新
编码中发现设计文档需修正时，主动更新设计文档后再继续编码，不悄悄偏离设计。
→ 更新 docs/design/

📈 持续优化策略（实践中迭代）
01
记录「偏离事件」
每当 Agent 在编码阶段发现设计文档不准确、需要临时决策并升级给人 —— 记录一次「偏离」。 统计偏离的类型和频率，识别 Spec 或技术设计阶段的系统性盲区。
📊 指标：偏离次数/功能 · 偏离类型分布
02
追踪「文档返修率」
统计 Spec 确认阶段需要几轮才能通过，技术设计文档被指出多少处修正。 如果某个项目 Spec 平均 3+ 轮才能确认，说明 PRD 质量或 Spec 模板需要改进。
📊 指标：确认轮数 · 单次修正点数
03
监控「切片粒度」
切片太大 → 单个切片耗时过长，反馈周期拉长。 切片太小 → 任务拆解开销占比过高。 收集每切片的实际耗时，找到「刚好够独立验证」的粒度甜点。
📊 指标：每切片平均耗时 · 切片数/功能
04
TDD 真实性审计
定期抽查：Agent 是否真的先跑了 RED，还是跳过了直接写实现？ 检查测试代码的覆盖率和 Mock 合理性——有没有"为了绿而绿"的假测试？ 每 3~5 个功能做一次抽样审计。
📊 指标：RED 跳过率 · 测试覆盖率 · Mock 合理性评分
05
建立「设计模式库」
把反复出现的领域模型、API 模式沉淀为 Skill 或参考模板。 例如：「标准 CRUD 设计模板」「多对多关联处理模式」「软删除设计约定」。 Agent 下次遇到同类需求时直接引用，减少重新推导。
📦 产出：Skill 文件 · 设计模板库
06
人机决策边界动态调整
初期保守——多确认。跑顺畅后逐步把低风险决策下放给 Agent。 例如：第 1~3 个功能严格走「技术设计必须确认」，后续如果偏离率 < 5%，降级为「仅通报不阻塞」。 以数据驱动，而非凭感觉调整。
🔄 机制：每 5 个功能评估一次，调整决策点策略
07
流程版本管理
流程本身是资产，需要版本化。每次调整后在 dev-mode-flow.md 头部记录版本号和变更摘要。 Agent 执行时读取当前版本，确保行为与文档一致。 实践 → 发现问题 → 更新流程 → 版本号+1。
📝 版本记录格式：v2.0 → v2.1 (2026-06-15) 调整切片粒度标准
08
事后回顾（Retro）
每个功能交付后做 5 分钟轻量回顾：
• 流程哪个阶段最耗时？
• 哪个阶段的产出返工最多？
• Agent 有没有问了不该问的问题（该自主的没自主）？
• Agent 有没有没问就该问的问题（该升级的没升级）？
📋 触发：每次 PR review 完成后自动生成回顾摘要

💡 设计理念：
• 人定义「做什么」和「关键决策」—— Spec 概要确认 + 设计方案方向 + 最终验收
• Agent 负责「怎么做」—— 80% 的文档推导、编码、测试
• 阶段 ① 核心原则：决策树先筛——能推导的不问，影响大的带选项问，模糊的才问。先概要后详细
• 不是把工作全扔给 Agent，而是让人聚焦在高价值的判断上
• 流程不是死的——持续优化策略确保它在实践中自我进化
